# Trinity V1.4.1 VTweak 运行时汉化

本工程生成独立的 `TrinityCN.asi`，不修改原始 `Trinity.asi`。英文到中文的映射只在开发阶段保存在
`translations.zh-CN.json`，构建时转换为 C++ 只读数据并编译进 ASI；发布目录禁止携带 JSON。
游戏内右上角版本号前、默认说明栏和 Windows 文件属性均带有 `b站up 改名_汉化` 标注。

物品添加、物品编辑和装备编辑中的动态物品名、分类名、仓库名不属于 Trinity 的静态字符串。
构建脚本会从当前受支持游戏版本的原版 `iteminfo`、`ItemGroupInfo`、`InventoryInfo` 与简体中文 PALOC 中生成
行号锁定的中文回退表，并把目录译文所需字形合并进 ImGui 字体范围。0.9.0.0 起同时生成“内部名称覆盖表”，
按 PABGB 记录的 `string_key` 命中检索，因此模组新增记录（行号在原版 6813 行之外）也能翻成中文。
命中优先级为“行号表 → 内部名称覆盖表 → 原 getter”，也就是内嵌表都没覆盖时必须把原函数的真实结果透传出去；
**绝不能再“未命中就返回 false”**——Trinity 收到 false 会退回“内部名美化”（下划线转空格 + 驼峰拆词），
这正是 0.8.0.0 里模组新增物品和特殊物品显示成片英文的原因。
当前 ItemInfo 中 72 个没有官方简中名称的开发、测试或特殊物品会使用人工中文名，并显示为
`[未收录] 中文名称`，用于提示它们可能无法由 Trinity 正常加入背包；已有官方名称的物品不会添加该标记。
标记本身也必须是中文，界面上不允许出现英文残留。
“添加物品”的一级分类继续使用已验证的精确 RVA 定点翻译与动态 ItemGroupInfo 回退，不直接轮询或
改写 Trinity 的最终分类向量。

当前锁定数据（Crimson Desert 2.02.00）：

- ItemInfo 6813 条 → 6813 条中文名（官方简中 6741，人工 `[未收录]` 回退 72）。
- ItemGroupInfo 1600 条 → 1600 条中文分类名（3 条开发分类用人工译名补齐）。
- InventoryInfo 21 条 → 21 条中文仓库名。
- 内部名称覆盖表 5 条：模组自制武器 `Custom_Dandelion_OP`、`Custom_White_Wind_Rapier_OP`、
  `Custom_Sigremon_Greataxe_OP`、`Custom_Greathammer_of_Fire_OP`、`Custom_DragonSlayer_OP`，
  它们在原版 `item.paloc` 里只有英文名，按官方简中同类武器命名译为“丹提利恩·超模”等。
- 生成时会读取加载器最近写出的 VFS 覆盖快照（`.cdloader/vfs_active/snapshot-*`）复核游戏实际加载的合并表：
  前 6813 行记录 key 必须与原版一致，且 12670 行物品、1600 行分类、21 行仓库不允许存在
  “只能显示英文且没有覆盖译名”的名称；没有快照时跳过该复核。

## 构建

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -ExecutionPolicy Bypass -File '.\tools\trinity_localizer\build_trinity_localizer.ps1'
```

构建产物固定为：

```text
dist/trinity_localizer/TrinityCN.asi
```

将其与 `Trinity.asi` 一起交给游戏的 ASI Loader 加载。当前实现严格匹配 Trinity `v1.4.1 (vTweak by Lian)`
（Lian fork）和 ImGui `1.91.5 (19150)`，动态目录数据严格匹配当前锁定的 Crimson Desert 2.02.00 数据表。
目标版本、字体函数序言、名称 getter 序言或游戏数据表哈希不一致时会自动拒绝对应功能，不修改 Trinity 的
功能逻辑。

## 已重新推导的 V1.4.1 锚点

每个新 Trinity 版本都当作全新二进制：V1.3.2 的 RVA 全部作废，下表地址均在当前 `Trinity.asi` 上
独立重新定位并逐字节核对。

| 项目 | 值 |
| --- | --- |
| 目标版本串 | `v1.4.1 (vTweak by Lian)` @ RVA `0x1A8B50` |
| 版本 LEA（唯一引用） | RVA `0x7E480`，`48 8D 3D C9 A6 12 00` |
| `AddFontFromFileTTF` | RVA `0xCCCC0`，17 字节序言 `40 55 53 56 57 41 56 41 57 48 8D AC 24 38 FF FF FF` |
| 名称 getter | RVA `0x457C0`，23 字节序言（含一条检查目录全局的 RIP 相对 `cmp`） |
| 名称 getter 调用点 | 9 处：`0x307A0`、`0x30DA3`、`0x334FB`、`0x35614`、`0x41DC5`、`0x459D5`、`0x472A2`、`0x47558`、`0x4C2D6` |
| 目录名称池全局 | `0x247398` |
| ItemInfo / ItemGroupInfo / InventoryInfo 表全局 | `0x247370` / `0x247380` / `0x247390` |
| 表加载调用点 | ItemInfo `0x30778`、ItemGroupInfo `0x34654`、stringinfo `0x42169` |
| definitions 数组加载 | helper `0x40990`：`*(全局)` → 表对象，count `+0x08`，数组 `+0x58`，失败回退 `+0x50` |
| 表结构 | count `+0x08`，definitions `+0x58`，物品名 `+0x20`，分类名 `+0x18`，仓库名 `+0x70` |

VTweak fork 自带 `Trinity_*.ini` 多语言覆盖，但本伴生补丁不依赖该文件，而是直接覆盖完整静态
菜单文本；动态物品名、分类名与仓库名通过 Hook 名称 getter（`0x457C0`）按游戏表行号查中文回退表。
物品使用 ItemInfo 定义 `+0x20`（表全局 `0x247370`），分类使用 ItemGroupInfo 定义 `+0x18`
（表全局 `0x247380`），仓库使用 InventoryInfo 定义 `+0x70`（表全局 `0x247390`）。
`0x457C0` 的 23 字节序言含一条 RIP 相对 `cmp`（检查目录全局 `0x247398`），跳板复制后会重定位该 `disp32`。

0.9.0.0 起直接把原函数（跳板）当作回退调用：9 个调用点全部只传三个寄存器参数
（`rcx` = `definitions[row]` + 字段偏移，`rdx` = 输出缓冲，`r8` = 容量；物品与分类容量 `0x40`，
仓库 `0x60`），反汇编确认该函数只读 `rcx/rdx/r8`，其余栈访问都是它自己栈帧里的临时量
（`rsp+0x20` / `+0x28` / `+0x88`，其中 `+0x88` 先写后读），因此跳板调用不会读脏栈。

每次游戏启动都会在 `bin64/TrinityCN.log` 覆盖写入运行诊断，包括分类/仓库地址表建立数量和
动态目录中文回退的首次命中结果；该日志不包含游戏存档或用户隐私数据。

旅行传送的顶层分类由 Trinity 在 `kSceneRules` 中硬编码，并非游戏本地化表字段；构建时按当前
V1.4.1 二进制中逐项验证过的 UTF-8 字符串槽翻译。分类内地点仍可能来自场景 key、地区缩写、
固定场景名或游戏节点原名，需按各自生成模式分别处理。

## V1.4.1 静态构建基线（2026-09-17）

- 目标 `Trinity.asi`：`v1.4.1 (vTweak by Lian)`，2,464,256 字节，SHA-256
  `54D518FB2C26C1ACCCFF3421DC20C123E27049B90F8D98B545E9513B29A92772`；ImageBase
  `0x180000000`，`.text` VA `0x1000` / RawPtr `0x400`，`.rdata` VA `0x129000` / RawPtr `0x128400`。
- 伴生 ASI 版本号为 `0.8.0.0`；`translations.zh-CN.json` 共 914 条定点翻译，全部按 V1.4.1 重新定位，
  旧版本中已不存在的字符串（`Dye applied`、`Socket cleared`、`Mount 2/3/4`、`All Categories` 等）
  以及只作为查找键、从不参与显示的字符串（`Armor`、`Gloves`、`Boots`、`Money`、`Critical` 等）
  均不得重新加入，否则会破坏 Trinity 的哈希比较。
- 动态目录生成实测：物品 6813/6813（官方 6741，`[mod]` 回退 72）、分类 1597/1600、仓库 21/21；
  生成时会校验游戏 EXE 与 9 张原版资源（6 张表 + `gamedata/item.paloc`、`itemgroup.paloc`、
  `inventory.paloc`）的 SHA-256。
- 作者 INI 审计：`Trinity_zh.ini` 共 688 个界面键，627 个存在于 V1.4.1 二进制；未被覆盖的仅
  `Name`、`Code` 两个元信息键，加上 7 个只作查找键、按设计不翻译的条目，视为清零。审计必须同时
  检查功能标题和紧邻说明，不能只因标题已汉化就认为该功能覆盖完成。
- 本版本不安装、不依赖作者的 `Trinity_zh.ini`；该文件只用作开发阶段的翻译覆盖审计参考。
- 结论边界：以上是静态构建与字节级校验记录，**尚未做实机显示测试**。
- 0.7.0 的“等待最终分类向量并直接写入”会导致严重卡顿，尤其是“物品 > 添加”页面；稳定版已
  移除这条链路。后续不得恢复 55 项全命中门槛、分类向量轮询或直接写入，也不得用整表后台预载
  替换此前多版本验证过的按需动态目录 Hook，除非有独立实现、性能证据和完整实机回归。

## 0.9.0.0 动态目录补全（2026-09-18）

- 症状：菜单“物品 > 添加”里出现成片英文，模组自制武器显示为 `Custom White Wind Rapier OP`
  这类内部 key 美化名。
- 根因：0.8.0.0 的目录 Hook 在内嵌表未命中时直接 `return false`；调用方拿到 `al=0` 会退回 Trinity
  的“内部名美化”（`0x3352F` 读 `definitions[row]+0x08` 的 `string_key` 后下划线转空格 + 驼峰拆词），
  于是原版 6813 行之外的模组新增记录（合并表实测 12670 行）和 72 条没有官方简中名的物品全部显示英文。
- 修复：`HookedCatalogLocString` 改为“行号表 → 内部名称覆盖表 → 原 getter”三级，原 getter 经跳板
  调用后只透传结果，不再阻断；`BuildCatalogAddressTable` 补齐 `0x40990` 的 `+0x50` 备用数组分支。
- 新增内部名称覆盖表：按 `string_key` 命中，覆盖 5 条原版 PALOC 只有英文名的模组自制武器。
- 未收录标记由 `[mod] ` 改为中文 `[未收录] `，界面上不再出现英文字符。
- 校验：在合并快照 `snapshot-77e0775cf805ceaf-fa2e24a1e337` 上复核 12670 行物品、1600 行分类、
  21 行仓库全部有中文；生成计数物品 6813/6813、分类 1600/1600、仓库 21/21、内部名称覆盖 5 条。
  产物 `dist/trinity_localizer/TrinityCN.asi` 614,912 字节，版本 `0.9.0.0`，SHA-256
  `2220E6144264ECA1D17CFCFEA0D53B4803C6763B423472B1339C59A03E306B04`。
- 实机确认点：`bin64/TrinityCN.log` 应出现“内部名称覆盖表已装载：5 条。”，首次取物品名后出现
  “物品中文地址表已建立：6813 条。”；若未命中内嵌表，还会出现“未命中内嵌表时已回退到原函数”。
- 结论边界：以上是静态构建与合并表字节级校验，**实机显示仍以用户机器为准**。
- 已知边界：旅行传送页面分类内的地点仍可能来自场景 key、地区缩写或固定场景名，未纳入本轮补全。

## 后续 Trinity 更新的强制重分析原则

每次 Trinity 发布新版本，都必须把新 `Trinity.asi` 当作全新的二进制目标，从底层重新走完分析，
不能因为更新日志只写了少量新功能，就只迁移旧 RVA 或补那几条文案。旧版本只能用于比较行为和确认
哪些设计曾经稳定，不能直接继承其地址、容量、调用约定、表结构、分类数量或汉化覆盖结论。

新版本发布汉化前至少重新确认：PE 哈希和版本、section 布局、全部界面字符串及相邻说明、作者 INI
与当前二进制/翻译表的全量差集、字体与版本锚点、动态名称 getter 调用链、表全局与字段偏移、硬编码
分类和旅行规则、游戏表生成数量、Hook 跳板重定位安全，以及菜单和“物品 > 添加”页面的实机性能。
任何实验性轮询、直接改写运行时容器或预载机制，都不得混入常规版本迁移；必须单独验证性能与稳定性。
